# Task 10: Feature E2E scenarios

## Required Skills

Перед выполнением задачи загрузи:
- `/skill:code-writing` — [skills/code-writing/SKILL.md](~/.claude/skills/code-writing/SKILL.md)

## Description

Это приёмка фичи 0011 автотестами. К моменту старта задачи весь продукт уже собран: модель
данных и миграция (Task 3), чистая логика перестановки и разрешения названия (Tasks 4–5),
отображение названий (Task 6), доска в заданном порядке с атрибутом `data-group-container`
(Task 7), попап настроек со строками `data-settings-group`, полем названия и стрелками
(Task 8), а существующие E2E уже переведены с поиска по названиям групп на идентификаторы
(Task 9). Новый файл `tests/e2e/0011-group-customization.spec.ts` покрывает поведение фичи
целиком — по списку из tech-spec, раздел Testing Strategy / E2E tests.

Два обстоятельства делают эту задачу не рутинной, и их нужно держать в голове от первой
строки:

**Первое — сценарий перетаскивания несёт основной вес.** Главный риск фичи в том, что смена
порядка групп способна пересоздать DOM-элементы, к которым привязана SortableJS, и
перетаскивание отвалится. Выбранный подход (CSS `order`, Decision 1) должен этот риск снять,
но единственное доказательство — тест, который **в той же сессии, без перезагрузки** меняет
порядок и тут же тащит задачу в обе стороны, обязательно с участием сворачиваемой группы
(`backlog` / `completed`) — у них привязка устроена иначе и ломается вероятнее. User-spec
прямо предупреждает: проверка вида «задать порядок → перезагрузить → перетащить» покажет
зелёный результат при сломанном продукте, потому что после перезагрузки библиотека
инициализируется заново на уже правильном порядке. Ни одного `page.goto()`, ни одного
`resetData()` между сменой порядка и перетаскиванием быть не должно.

**Второе — проверять порядок по индексу элемента бессмысленно.** По Decision 12 порядок
задаётся CSS-свойством `order` на существующих обёртках, DOM-последовательность блоков в
`BoardLayout.svelte` при этом не меняется никогда. Значит `locator.nth(0)` и любые проверки
«кто раньше в DOM» на доске пройдут одинаково и до, и после настройки — то есть не докажут
ничего. Порядок на доске проверяется вычисленным значением `order` и/или экранной геометрией.
Важная оговорка: это относится **только к доске**. В попапе настроек строки рендерятся
циклом по сконфигурированному порядку, там DOM-последовательность настоящая, и проверять
порядок строк по их последовательности в DOM — правильно.

Адресация групп в новых сценариях — только по идентификаторам: `[data-group-container="…"]`
на доске, `[data-settings-group="…"]` в попапе. Поиск по отображаемому названию запрещён:
в этих сценариях названия ровно то, что меняется.

   - **Сц.4 видимая группа перепрыгивает скрытую с первого нажатия.** Скрыть группу, стоящую

     нажатия»: второе нажатие не делать.
   - **Сц.5 перетаскивание работает сразу после смены порядка, без перезагрузки** — ключевой
     сценарий, требования в п. 5.
   - **Сц.6 повторное открытие попапа сохраняет порядок строк.** Задать порядок, в котором

     последовательность значений `data-settings-group` и сверить с ожидаемой: скрытая строка
     стоит на своей позиции, а не съехала в конец списка.
   - **Сц.7 «Отмена» откатывает несохранённые название и порядок.** Изменить название и

     открытии попапа поле показывает сохранённое значение, а строки — сохранённый порядок.
   - **Сц.8 клик мимо попапа откатывает то же самое.** То же, но закрытие кликом по

     задать ей другие, вернуться на A и убедиться, что настройки A на месте и не протекли.
   - **Сц.10 название из 40 символов не ломает строку заголовка.** Снять высоту заголовка
     группы с дефолтным названием, задать 40 символов, сохранить, снять высоту снова —
     не изменилась (нет переноса на вторую строку); текст усечён (`scrollWidth` элемента
     заголовка больше его `clientWidth`), а ширина элемента заголовка не вылезает за ширину
     обёртки группы.
   - **Сц.11 переключение видимости меняет поведение стрелок до сохранения.** В одном
     открытии попапа: снять видимость с группы-соседки и **не сохраняя** нажать стрелку у
     видимой группы. Ожидание — стрелка сработала по новому, несохранённому состоянию, то
     есть перепрыгнула только что скрытую группу. Проверить по порядку строк в попапе (до
     сохранения доска ещё старая), затем сохранить и подтвердить результат на доске.
   - **Сц.12 попап с полным списком строк не выходит за экран, тело прокручивается.** Задать
     невысокий viewport, открыть попап, проверить: его `boundingBox` целиком внутри вьюпорта
     по вертикали, а у прокручиваемого контейнера `scrollHeight > clientHeight` и прокрутка
     реально происходит (после `scrollTop`-сдвига значение изменилось).

4. **Симуляция перезагрузки — только через сохранённые данные.** Прямой `page.goto('/')` для
   проверки сохранности не годится: харнесс на старте инициализируется из `migrateData(null)`
   и не читает `localStorage`, поэтому «перезагрузка» просто обнулит доску, и тест на
   сохранность станет ложно-зелёным либо ложно-красным. Правильный способ: прочитать снимок
   из `localStorage['tm-test-data']`, затем передать его в `window.__test.resetData(снимок)` —
   у снимка есть поле `version`, поэтому харнесс прогонит его через `migrateData` и
   перерисует доску из сохранённых данных. Это и есть настоящая проверка круга
   «сохранили → загрузили → отрисовали».

5. **Сценарий перетаскивания (Сц.5) — требования, от которых нельзя отступать:**
   - Порядок шагов строго такой: создать задачи → сменить порядок групп через попап и
     сохранить → **сразу** перетащить. Никакой перезагрузки, никакого `resetData`, никакого
     `page.goto` между сменой порядка и перетаскиванием.
   - Перетаскивание — настоящим вводом мыши, через SortableJS. `window.__test.moveTask`
     (и хелпер `moveTask` из `helpers.ts`) в этом сценарии использовать **запрещено**: он
     дёргает стор напрямую, минуя библиотеку, и проверяет ровно то, что не сломано.
   - Перетащить **в обе стороны**: A → B и B → A.
   - Обязательно задействовать сворачиваемую группу: перетащить между обычной группой и
     `backlog` (или `completed`), предварительно развернув её через `expandGroup`.
   - Дополнительно — проверка сохранности DOM-узлов: перед сменой порядка пометить тела групп
     (`[data-group-id]`) полем-меткой прямо на DOM-узле через `page.evaluate`, после смены
     порядка убедиться, что метка на месте. Это подтверждает механизм из Decision 1 (узлы не
     пересоздаются), но **не заменяет** настоящее перетаскивание, а дополняет его.
   - Если настоящее перетаскивание в харнессе не заводится с первого подхода — разбираться
     (см. Implementation hints), а не подменять его на `moveTask`. Если после честных попыток
     оно принципиально невозможно — остановиться и доложить, а не сдать зелёный тест, который
     ничего не проверяет.

6. Прогнать `npx playwright test tests/e2e/0011-group-customization.spec.ts` — весь набор
   зелёный. Затем прогнать `npx playwright test` целиком и убедиться, что новый файл не

## TDD Anchor

Тесты здесь — сам продукт задачи, поэтому классический цикл «красный до кода» неприменим:
код уже написан предыдущими волнами. Вместо него обязателен **негативный контроль**: каждое
утверждение должно быть доказано способным падать. Тест, который проходит в обоих
состояниях мира, — это не тест, а строчка в отчёте.

Порядок работы по каждому сценарию: написать → убедиться, что он зелёный на текущем
продукте → временно сломать условие → убедиться, что он покраснел → вернуть как было.

Обязательный минимум негативного контроля:

- `tests/e2e/0011-group-customization.spec.ts::Сц.3` — временно убрать сохранение
  (не нажимать «Сохранить» после стрелки) → утверждение о порядке на доске должно упасть.
  Если оно проходит и без сохранения, значит проверка смотрит на DOM-индекс, а не на `order`,
  и её надо переписать (Decision 12).
- `tests/e2e/0011-group-customization.spec.ts::Сц.4` — временно не нажимать стрелку вовсе →
  тест должен упасть.
- `tests/e2e/0011-group-customization.spec.ts::Сц.5` — временно закомментировать шаг смены
  порядка → тест должен остаться зелёным (перетаскивание работает и без перестановки); затем
  временно вставить перезагрузку между перестановкой и перетаскиванием → тест обязан остаться
  зелёным тоже, и это тот самый ложно-зелёный вариант, ради отличия от которого сценарий
  написан. Убедись, что в финальной версии перезагрузки нет.
- `tests/e2e/0011-group-customization.spec.ts::Сц.10` — временно задать название в 5 символов

**Edge cases:**
- **Свёрнутая группа отсутствует в DOM.** У `backlog` и `completed` тело `[data-group-id]`
  появляется только в развёрнутом виде. Обёртка `[data-group-container]` при этом есть
  всегда — на ней и держатся проверки порядка. Для перетаскивания группу нужно сначала
  развернуть (`expandGroup`).
- **Последняя видимая группа.** Чекбокс видимости у единственной оставшейся видимой группы
  отключён (`0006`, Сц.9) — в Сц.4 и Сц.11 не доводи набор до одной видимой.
- **Отключённые стрелки.** У крайней группы стрелка в соответствующую сторону неактивна.
  Выбирай для перестановки группу из середины порядка, иначе клик по `disabled`-кнопке
  просто ничего не сделает, а тест покажет «порядок не изменился» и будет прав.
- **Скрытые строки в попапе остаются кликабельными.** Скрытая группа двигается стрелками по
  соседям списка — это ожидаемое поведение, не баг.
- **Пары половинной ширины перепаковываются.** После смены порядка `focus`/`inProgress` могут
  перестать быть парой, и класс обёртки сменится на `--half-alone`. Не завязывай проверки
  порядка на классы ширины — только на `order` и геометрию.
- **Геометрия и одна строка.** Две группы половинной ширины в одной строке имеют одинаковый
  `top`. Для них сравнивай `left`, а не `top`; для групп в разных строках — `top`. Надёжнее
  всего сравнивать ранг по `order`, а геометрию использовать как подтверждающую проверку.
- **`order` возвращается строкой.** `getComputedStyle(el).order` — строка (`"3"`); приводи к
  числу перед сравнением. Значение по умолчанию — `"0"`.
- **Одинаковые названия у разных групп допустимы** (user-spec). Не пиши утверждений,
  предполагающих уникальность названий.
- **Общий `localStorage` между тестами.** `standardBeforeEach` чистит данные и снимает
  зависшие оверлеи модалок; не забывай его в `beforeEach`, иначе набор станет
  порядко-зависимым.
- **Узкий viewport.** В Сц.12 не опускайся ниже 600px по ширине: медиазапрос переводит все
  группы в полную ширину (`0007`, Сц.21) и меняет раскладку. Уменьшай **высоту**, ширину
  оставь обычной. После `setViewportSize` дай кадру перерисоваться.
- **40 символов ровно.** Это верхняя граница ввода (`maxlength`). Строка должна быть заметно
  шире колонки заголовка, иначе усечения не будет и проверка станет бессмысленной — бери
  40 символов без пробелов.

**Implementation hints:**
- Ранг группы удобно считать одним `page.evaluate`: собрать все `[data-group-container]`,
  для каждого взять `dataset` и `getComputedStyle(el).order`, вернуть массив пар, а сортировку
  и сравнение делать уже в тесте. Один вызов на утверждение — меньше гонок, чем десяток
  точечных запросов.
- Настоящее перетаскивание в Chromium: навести на карточку (`locator.hover()`),
  `page.mouse.down()`, затем **несколько** `page.mouse.move(x, y, { steps: … })` — первый
  небольшой сдвиг, чтобы библиотека распознала жест, потом движение к центру тела
  группы-приёмника, потом ещё один `move` в ту же точку, и `page.mouse.up()`. Одного `move`
  почти всегда мало. Целевая точка — центр `[data-group-id="…"]` приёмника; если группа
  пустая, целься в её тело, а не в заголовок.
- Если карточка не «схватывается»: проверь, что тащишь за саму карточку, а не за кнопку
  удаления (`.tm-task-card__delete` стоит в `filter` SortableJS), и что тело группы-приёмника
  реально в DOM и видимо.
- Результат перетаскивания проверяй по данным, а не по DOM сразу после `mouse.up()`:
  SortableJS откатывает DOM и отдаёт ход Svelte (см. `useSortable.ts`), поэтому надёжнее
  дождаться `expect(...).toHaveCount(...)` на карточках в группе-приёмнике, а не читать DOM
  синхронно.
- Метку для проверки сохранности DOM-узлов ставь как свойство на самом элементе
  (`el.__tmProbe = 1`) через `page.evaluate` — атрибут Svelte может перезаписать при
  ре-рендере, свойство переживает только тот же самый узел.
- Заголовок группы: обычные группы — `.tm-group-header__title`, сворачиваемые —
  `.tm-collapsible-group__title`. Ищи их внутри `[data-group-container="…"]`, тогда один
  хелпер закроет оба случая.
- Заголовок попапа настроек группы — тот же `.tm-popup__title`, что и у настроек доски;
  различай их по тому, каким способом попап открыт (`openGroupSettings` против
  `openBoardSettings`), а не по тексту.
- Прокручиваемый контейнер попапа в Сц.12 определи по факту (`scrollHeight > clientHeight`),
  а не по угаданному имени класса: точное имя задаёт Task 8.
- Не добавляй в `helpers.ts` ничего нового: Task 9 только что привёл этот файл в порядок, а
  твои хелперы специфичны для одной фичи. Держи их в spec-файле.
- Не расширяй `window.__test`: это чужой файл (`tests/harness/main.ts`) и чужая волна.
  Если чего-то принципиально не хватает — сначала доложи, а не правь харнесс молча.
