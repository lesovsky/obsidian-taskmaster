# Obsidian TaskMaster — техническая спецификация

## Стек технологий

| Компонент | Технология | Обоснование |
|-----------|-----------|-------------|
| **Язык** | TypeScript | Стандарт для Obsidian-плагинов, типизация снижает количество ошибок |
| **UI-фреймворк** | Svelte | Компилируется в чистый JS (нет runtime), реактивность из коробки, популярен в экосистеме Obsidian |
| **Drag-and-drop** | SortableJS | Framework-agnostic, touch-поддержка, сортировка + перемещение между группами, ~10KB gzipped |
| **Сборка** | esbuild | Стандарт для Obsidian-плагинов, быстрая сборка |
| **Мин. версия Obsidian** | 1.0.0 | Стабильный API: ItemView, loadData/saveData, Command Palette, ribbon |

### Типы данных (TypeScript)

```typescript
// Приоритеты
type Priority = 'low' | 'medium' | 'high';

// Статусы
type Status = 'new' | 'inProgress' | 'waiting' | 'meeting' | 'completed';

// Идентификаторы групп
type GroupId = 'backlog' | 'focus' | 'inProgress' | 'orgIntentions' | 'delegated' | 'completed';

// Режим отображения карточек
type CardView = 'default' | 'compact';

// Лейаут карточек (количество колонок)
type CardLayout = 'single' | 'multi';

// Пункт пост-задачи — хранится внутри задачи, а не отдельной записью в tasks
interface FollowUp {
  id: string;             // UUID самого пункта
  text: string;           // Текст пункта: обрезан по краям, 1–200 символов
  createdTaskId: string;  // '' — пункт ещё не заведён; иначе UUID задачи, созданной из пункта
}

// Задача
interface Task {
  id: string;           // UUID
  what: string;         // Описание задачи (многострочный текст, обязательное поле, макс. 10 000 символов)
  why: string;          // Цель (многострочный текст, макс. 10 000 символов)
  who: string;          // Исполнитель (свободный текст, макс. 200 символов)
  deadline: string;     // Дедлайн, формат "YYYY-MM-DD", пустая строка если не задан
  createdAt: string;    // Дата создания, формат "YYYY-MM-DD", заполняется автоматически
  completedAt: string;  // Дата завершения, формат "YYYY-MM-DD", пустая строка если не завершена
  priority: Priority;   // Приоритет, по умолчанию берётся из глобальных настроек
  status: Status;       // Статус
  followUps: FollowUp[]; // Пост-задачи — что сделать после выполнения, макс. 20 пунктов (см. «Пост-задачи»)
}

// Группа
interface Group {
  taskIds: string[];              // Упорядоченный массив UUID задач
  wipLimit: number | null;        // WIP-лимит, null = без лимита
  collapsed: boolean;             // Свёрнута ли группа (для backlog и completed)
  completedRetentionDays: number | null; // Срок хранения завершённых (только для completed)
  fullWidth: boolean;             // true = полная ширина, false = половина
  title: string;                  // Пользовательское название группы на этой доске (не Board.title);
                                  // '' = показывать дефолтное локализованное название, макс. 40 символов
}

// Доска
interface Board {
  id: string;                     // UUID
  title: string;                  // Название доски
  subtitle: string;               // Подзаголовок (может быть пустым)
  hiddenGroups: GroupId[];        // Список скрытых групп (по умолчанию [])
  notes: string;                  // Текст секции Notes (по умолчанию пустая строка)
  notesCollapsed: boolean;        // Свёрнута ли секция Notes (по умолчанию true)
  notesHidden: boolean;           // Скрыть секцию Notes полностью (по умолчанию false)
  groupOrder: GroupId[];          // Порядок отрисовки групп на этой доске — всегда перестановка
                                  // шести известных идентификаторов, по умолчанию порядок GROUP_IDS
  groups: Record<GroupId, Group>; // 6 фиксированных групп
}

// Глобальные настройки
interface Settings {
  language: LanguageSetting;      // Язык интерфейса ('auto' | 'en' | 'ru')
  defaultPriority: Priority;      // Приоритет по умолчанию
  cardView: CardView;             // Режим отображения карточек
  cardLayout: CardLayout;         // Лейаут карточек: одна колонка или мультиколоночный
}

// Корневая структура data.json
interface PluginData {
  version: number;                // Версия схемы данных для миграций
  settings: Settings;
  boards: Board[];
  tasks: Record<string, Task>;    // Плоский словарь всех задач всех досок
}
```

### Хранение задач — плоский словарь

Все задачи всех досок хранятся в одном плоском объекте `tasks` (ключ — UUID). Группы ссылаются на задачи через массивы `taskIds`.

**Почему не вложенные в доски:**
- Перемещение между группами — изменение только массивов `taskIds`, объект задачи не трогается
- Нет дублирования данных
- Простой доступ к задаче по ID: `data.tasks[taskId]`

### Модальные окна

Модальные окна используют стандартный Obsidian `Modal` (закрытие по Escape, клик вне окна, стили темы). Внутрь монтируется Svelte-компонент с формой:

```typescript
class TaskModal extends Modal {
  onOpen() {
    new TaskFormContent({
      target: this.contentEl,
      props: { task, groupId, defaultPriority, onSave, onDelete }
    });
  }
}
```

`onSave` получает два аргумента — `(task, spawnItemIds)`. Второй аргумент содержит id пунктов пост-задач, которые в форме помечены «→ в бэклог» и остались после нормализации списка. Форма в store не пишет. `BoardLayout` сначала сохраняет задачу (`addTask` или `updateTask`), затем передаёт эти id в `createFollowUpTasks` и показывает уведомление. Escape закрывает окно без вызова `onSave` и тем самым отбрасывает и правки списка, и пометки.

Аналогично для popup'ов настроек группы и доски.

## Управление состоянием (Svelte Stores)

Три store для разделения ответственности:

| Store | Содержимое | Сохраняется в файл? |
|-------|-----------|---------------------|
| **dataStore** | Доски, задачи, настройки — все данные из data.json | Да, при каждом изменении |
| **uiStore** | Активная доска, открытые модалки, очередь toast'ов | Нет |
| **pluginStore** | Ссылка на экземпляр плагина (доступ к saveData(), Modal API) | Нет |

## Drag-and-drop: синхронизация SortableJS и Svelte

SortableJS манипулирует DOM напрямую, Svelte управляет DOM через реактивность. Чтобы избежать конфликтов, используется стратегия «отмена + обновление»:

1. SortableJS ловит жест перетаскивания и определяет: откуда, куда, на какую позицию
2. DOM-изменения SortableJS **отменяются** (элемент возвращается на исходное место)
3. Обновляется `dataStore` (массивы `taskIds` в группах)
4. Svelte реагирует на изменение store и **сам перерисовывает** доску в правильном порядке

SortableJS — «уши» (слушает перетаскивание), Svelte — «руки» (рисует результат).

## Создание задачи

Нажатие «+» в группе → открывается Obsidian Modal с формой:

**Предзаполненные автоматически:**
- ID → `crypto.randomUUID()`
- Статус → `new` (бэклог) или `inProgress` (рабочие группы) — по правилам переходов
- Приоритет → из глобальных настроек (по умолчанию `medium`)
- Дата создания → сегодня (`YYYY-MM-DD`)

**Заполняет пользователь:**
- **Что** — обязательное поле, кнопка «Сохранить» неактивна пока пустое
- **Зачем** — необязательное
- **Кто** — необязательное
- **Когда** (дедлайн) — необязательное
- **После выполнения** — необязательный список пост-задач (см. «Пост-задачи»)

Задача добавляется в конец массива `taskIds` той группы, где нажали «+».

## Удаление задачи (Toast-механизм)

1. Пользователь нажимает «Удалить»
2. UUID задачи убирается из `taskIds` группы → `saveData()` → задача исчезает с доски
3. Объект задачи **остаётся** в словаре `tasks` (временно осиротевший)
4. Появляется toast (7 секунд с обратным таймером)
5. **Отмена** → UUID возвращается в `taskIds` на прежнюю позицию → `saveData()`
6. **Таймер истёк** → объект удаляется из `tasks` → `saveData()`

Если Obsidian закрыли за эти 7 секунд — задача останется осиротевшей и будет удалена функцией очистки при следующем запуске.

**Toast-стакинг:**

- Максимум **3 toast'а** одновременно на экране
- Новые появляются снизу, старые сдвигаются вверх
- Если удалить 4-ю задачу при 3 активных toast'ах — самый старый toast исчезает (задача удаляется окончательно), освобождая место для нового

### Отмена быстрого завершения (☑)

Кнопка ☑ ставит toast типа `complete` в ту же очередь (`Toast = DeleteToast | CompleteToast` в `uiStore`). Кроме позиции и прежних `status` и `completedAt`, он хранит `spawnedTaskIds` — id задач, которые это завершение завело из пост-задач. `quickCompleteTask` возвращает их вместе с данными для отмены.

«Отменить» вызывает `undoQuickComplete(..., spawnedTaskIds)`, параметр обязательный. В том же обновлении store `revertSpawnedFollowUps` удаляет эти задачи из `tasks` и из любой группы доски: пользователь мог успеть их перетащить. Пункты родителя, которые указывают на удалённые задачи, возвращаются в состояние «не заведено». Пункты, заведённые раньше из формы, остаются как были: сопоставление идёт по `createdTaskId`, а не по позиции. Если заведённую задачу уже удалили, её просто пропускают.

После этого `BoardLayout` убирает живые toast'ы удаления и завершения этих задач и гасит их таймеры. Иначе их «Отменить» вернул бы в группу id задачи, которой больше нет. У перетаскивания в «Завершённые» отмены нет, как и раньше.

## Удаление доски

- Показывается стандартный диалог подтверждения: «Удалить доску "Проект Alpha" и все её задачи?»
- При подтверждении: удаляется доска из массива `boards`, все её задачи удаляются из `tasks`
- Нельзя удалить последнюю доску — хотя бы одна должна существовать всегда

## Создание доски

Нажатие «+» в заголовке:

1. Создаётся новая доска с локализованным названием по умолчанию, пустым `subtitle`, `hiddenGroups: []`, `notesHidden: false`, порядком групп по умолчанию (`groupOrder` = порядок `GROUP_IDS`) и 6 пустыми группами с дефолтными настройками (в том числе с пустым `title` у каждой)
2. `saveData()`
3. Активная доска переключается на новую

## Очистка данных при загрузке

При каждой загрузке плагина последовательно выполняются:

1. **Миграция данных** (`migrateData()`) — обновление схемы при необходимости
2. **Автоочистка завершённых** — удаление задач старше `completedRetentionDays` из группы «Завершённые»
3. **Очистка осиротевших задач** — сбор всех `taskIds` из всех групп всех досок, удаление из `tasks` записей, которые не упоминаются ни в одной группе

```typescript
function cleanupOrphanedTasks(data: PluginData): void {
  const usedIds = new Set<string>();
  for (const board of data.boards) {
    for (const group of Object.values(board.groups)) {
      group.taskIds.forEach(id => usedIds.add(id));
    }
  }
  for (const taskId of Object.keys(data.tasks)) {
    if (!usedIds.has(taskId)) {
      delete data.tasks[taskId];
    }
  }
}
```

## Сохранение данных

Сохранение через стандартный Obsidian API: `loadData()` / `saveData()`.

**Когда сохраняется:**

| Действие | Момент сохранения |
|----------|-------------------|
| Создание/редактирование задачи | При закрытии модального окна (кнопка «Сохранить») |
| Удаление задачи | Сразу при удалении + повторно через 7 сек (финальное удаление) или при отмене |
| Drag-and-drop | При завершении перетаскивания (событие drop) |
| Изменение настроек | При закрытии popup |
| Переключение свёрнутости группы | Сразу при переключении |

## Миграция данных

При загрузке плагина вызывается `migrateData()`:

```typescript
function migrateData(data: any): PluginData {
  const version = data.version ?? 0;

  if (version < 1) {
    data = migrateV0toV1(data);
  }
  if (version < 4) {
    data = migrateV3toV4(data);
  }
  if (version < 6) {
    data = migrateV5toV6(data);
  }
  if (version < 7) {
    data = migrateV6toV7(data);
  }
  if (version < 8) {
    data = migrateV7toV8(data);
  }
  if (version < 9) {
    data = migrateV8toV9(data);
  }

  // Санация выполняется здесь, вне версионных веток — см. ниже
  for (const board of data.boards) {
    board.groupOrder = sanitizeGroupOrder(board.groupOrder);
    for (const group of Object.values(board.groups)) {
      group.title = sanitizeGroupTitle(group.title);
    }
  }
  for (const task of taskObjects(data.tasks)) { // записи-не-объекты пропускаются
    task.followUps = sanitizeFollowUps(task.followUps);
  }

  return data as PluginData;
}
```

Миграции выполняются последовательно. После миграции данные пересохраняются. Имена `migrateVNtoVM` в этом разделе — приём изложения: в `src/data/migration.ts` каждая ветка написана прямо внутри `migrateData()`, отдельных функций с такими именами нет.

**Миграция v3 → v4** добавляет поле `hiddenGroups: []` к каждой существующей доске:

```typescript
function migrateV3toV4(data: any): any {
  for (const board of data.boards ?? []) {
    if (board.hiddenGroups === undefined) {
      board.hiddenGroups = [];
    }
  }
  data.version = 4;
  return data;
}
```

**Миграция v5 → v6** добавляет поле `cardLayout: 'single'` в настройки:

```typescript
function migrateV5toV6(data: any): any {
  if (!data.settings.cardLayout) {
    data.settings.cardLayout = 'single';
  }
  data.version = 6;
  return data;
}
```

**Миграция v6 → v7** добавляет поле `notesHidden: false` к каждой существующей доске. Секция Notes остаётся видимой после миграции — пользователь не заметит изменений:

```typescript
function migrateV6toV7(data: any): any {
  for (const board of data.boards ?? []) {
    if (board.notesHidden === undefined) {
      board.notesHidden = false;
    }
  }
  data.version = 7;
  return data;
}
```

**Миграция v7 → v8** добавляет пустое название `title: ''` каждой группе и порядок групп `groupOrder` каждой доске. Внешний вид существующих досок после миграции не меняется: пустое название означает «показывать дефолтное локализованное», а дефолтный порядок — это ровно та последовательность, которая до версии 8 была зашита в разметку:

```typescript
function migrateV7toV8(data: any): any {
  for (const board of data.boards ?? []) {
    for (const group of Object.values(board.groups)) {
      if (group.title === undefined) {
        group.title = '';
      }
    }
    if (board.groupOrder === undefined) {
      board.groupOrder = [...GROUP_IDS];
    }
  }
  data.version = 8;
  return data;
}
```

**Миграция v8 → v9** добавляет каждой задаче пустой список пост-задач `followUps: []`, если поля нет. Это первая ветка, которая обходит `tasks`. Запись задачи, которая не является объектом, она пропускает, а не чинит: более широкая защита загрузки — TD-01. Доски после миграции выглядят как раньше, потому что при пустом списке маркер `↪ N` на карточке не показывается.

Проверка `=== undefined` защищает от перезаписи значения, если поле уже присутствует в данных.

### Санация полей на каждой загрузке

Названия групп, порядок групп и списки пост-задач проверяются **при каждой загрузке**, а не один раз в версионной ветке: соответствующий блок в `migrateData()` стоит после всех веток `if (version < N)` и выполняется независимо от версии данных. (Второй безусловный доводчик в этой функции — подстановка `settings.cardView`, если поля нет; он проще и просто дописывает значение по умолчанию.)

Инварианты, которые он держит:

- `board.groupOrder` — ровно шесть известных идентификаторов, каждый по одному разу. Посторонние идентификаторы отбрасываются, дубликаты схлопываются на первое вхождение, недостающие дописываются в конец в порядке `GROUP_IDS`. Значение любого другого вида (поле отсутствует, `null`, не массив) заменяется на порядок по умолчанию
- `group.title` — строка, обрезанная по краям и ограниченная 40 символами (сначала `trim()`, потом обрезка по длине, чтобы пробелы вокруг длинного названия не съедали настоящие символы). Не-строка становится пустой строкой
- `task.followUps` — массив не длиннее 20 пунктов. Не-массив становится `[]`. Текст пункта обрезается по краям и до 200 символов, после обрезки снимаются хвостовые пробелы и одинокая старшая половина суррогатной пары. Пункт без текста (не строка или пусто после обрезки) отбрасывается, и лимит 20 считается только по оставшимся. Плохой `id` (нет, не строка, пустой, повтор) заменяется новым UUID: текст — содержимое пользователя, а `id` — служебная деталь. Не-строковый `createdTaskId` становится `''`, то есть пункт снова «не заведён». Валидный список проходит без изменений, поэтому повторная загрузка ничего не переписывает

Все три функции (`sanitizeGroupOrder`, `sanitizeGroupTitle`, `sanitizeFollowUps`) принимают `unknown` и никогда не бросают исключение: `migrateData()` выполняется до отрисовки доски, и исключение на повреждённых данных оставило бы пользователя вообще без доски. Сообщения о починке пользователю не показываются.

**Почему вне версионной ветки.** Версионная ветка отрабатывает один раз: после неё в файле стоит `version: 8`, и при следующей загрузке ветка `if (version < 8)` пропускается. Файл `data.json` правится руками — и порча, внесённая уже после миграции, никакой веткой не чинилась бы. Доска с посторонним идентификатором в `groupOrder` или с `null` вместо массива открывалась бы пустой. Санация вне ветки чинит такие данные при каждом открытии.

Санация повреждённого идентификатора восстанавливает его в списке порядка, но не восстанавливает сам объект группы: доску с вручную удалённым ключом группы миграция не воссоздаёт. Такие идентификаторы `BoardLayout` и `BoardSettingsPopup` просто не рисуют, проверяя наличие объекта группы перед отрисовкой. Полной устойчивости к ручной порче это не даёт: `cleanupCompletedTasks()` читает `board.groups.completed.completedRetentionDays` фиксированным путём и на доске с удалённой группой `completed` падает при загрузке, до всякой отрисовки.

Лимиты пост-задач объявлены в `src/data/migration.ts` (`FOLLOW_UP_TEXT_MAX_LENGTH`, `MAX_FOLLOW_UPS`), а `src/logic/followUps.ts` реэкспортирует их для формы. `finalizeFollowUpDrafts()` нормализует текст той же цепочкой, что и `sanitizeFollowUps()`, поэтому список, сохранённый формой, при следующей загрузке не меняется.

Ту же функцию `sanitizeGroupTitle()` вызывает `updateBoard()` в `dataStore` при сохранении настроек доски — правила нормализации названия одинаковы для обоих входов (набор текста в попапе и правка файла руками). Порядок при сохранении пишется как пришёл: его единственный источник — попап, который может выдать только перестановку известных идентификаторов.

## Автоматические переходы статусов

При перемещении задачи между группами (drag-and-drop) применяются правила:

```typescript
function applyStatusTransition(task: Task, fromGroup: GroupId, toGroup: GroupId): void {
  if (toGroup === 'completed') {
    task.status = 'completed';
    task.completedAt = formatDate(new Date()); // YYYY-MM-DD
  } else if (toGroup === 'backlog') {
    // при перемещении в бэклог статус не меняется
  } else if (fromGroup === 'backlog' && task.status === 'new') {
    task.status = 'inProgress';
  } else if (fromGroup === 'completed') {
    task.status = 'inProgress';
    task.completedAt = ''; // очищаем дату завершения
  }
  // перемещение между рабочими группами — статус не меняется
}
```

Автоматические переходы статусов применяются к задачам во всех группах независимо от их видимости. Скрытая группа остаётся полноценной группой с точки зрения логики.

## Пост-задачи (follow-ups)

Пункты «что сделать после выполнения» хранятся внутри задачи, в поле `Task.followUps`, а не отдельными записями в `tasks`. Отдельную запись, на которую не ссылается ни одна группа, удалила бы `cleanupOrphanedTasks()`. Связей между карточками нет: задача, заведённая из пункта, — обычная самостоятельная карточка.

Все правила собраны в чистом модуле `src/logic/followUps.ts`. Он не импортирует stores, i18n и `obsidian` и покрыт unit-тестами (`tests/unit/followUps.test.ts`). В модуле: выбор незаведённых пунктов (`pendingFollowUps`), построение задачи из пункта (`buildFollowUpTask`), заведение (`spawnFollowUps`) и откат (`revertSpawnedFollowUps`), превращение черновиков формы в сохраняемый список (`finalizeFollowUpDrafts`) и текст уведомления (`formatFollowUpNotice`). `spawnFollowUps` и `revertSpawnedFollowUps` меняют переданный `PluginData` на месте, как `applyStatusTransition` меняет задачу. `dataStore` остаётся тонкой обёрткой: каждая операция — один `update` и один `persist()`.

### Когда пункты заводятся

| Действие | Что заводится | Где в коде |
|----------|---------------|------------|
| ☑ на карточке | Все незаведённые пункты | `quickCompleteTask` |
| Перетаскивание в «Завершённые» из другой группы | Все незаведённые пункты | `moveTask`, условие `to === 'completed' && from !== 'completed'` |
| «Сохранить» в форме, где есть пункты с пометкой «→ в бэклог» | Только помеченные | `createFollowUpTasks(boardId, parentTaskId, itemIds)` |

Ничего не заводят:

- перестановка внутри «Завершённых». Она тоже проходит через `moveTask` и `applyStatusTransition`, поэтому проверка `from` обязательна;
- выбор статуса «Завершена» в форме (`updateTask`): задача остаётся в своей группе;
- повторное завершение: у всех пунктов уже заполнен `createdTaskId`.

Каждая операция возвращает id заведённых задач. Об уведомлениях store не знает.

### Поля заведённой задачи

- `what` — текст пункта
- `why` — префикс `followUps.whyPrefix` («After: » или «После: ») плюс `what` родителя, с обрезкой до 10 000 символов (лимит поля «Зачем»). Префикс берётся на языке интерфейса в момент заведения и дальше не переводится
- `who`, `deadline`, `completedAt` — пустые
- `priority` — `settings.defaultPriority`, `status` — `new`, `createdAt` — сегодня, `followUps` — `[]`

Задачи добавляются в конец `backlog.taskIds` той же доски в порядке пунктов, даже если бэклог скрыт. Бэклог при этом не разворачивается. У пункта заполняется `createdTaskId`. Маркер `↪ N` на карточке считает только пункты с пустым `createdTaskId`.

### Уведомление

На каждое действие показывается одно стандартное уведомление Obsidian (`Notice`), и только если что-то заведено. Его показывает `showFollowUpNotice(boardId, count)` из `src/ui/followUpNotice.ts` — это единственный модуль с импортом `Notice`. Импорт `obsidian` в store сломал бы unit-тесты: они загружают store в Node, где модуль `obsidian` не находится. Функцию вызывают `BoardLayout` (☑ и «Сохранить» в форме) и `moveTaskAndNotify` из `src/ui/useSortable.ts` (перетаскивание). Через `moveTaskAndNotify` идёт и `window.__test.moveTask`, поэтому E2E-тесты проверяют уведомление на том же пути.

Текст собирается из шаблона `followUps.noticeCreated` с плейсхолдерами `{group}` и `{count}`. Если бэклог на доске скрыт, через пробел добавляется `followUps.noticeHidden`. В `{group}` подставляется текущее отображаемое название бэклога через `resolveGroupTitle`, то есть с учётом переименования. Подстановка делается за один проход функцией-заменителем. Название группы — пользовательский текст, и `$&` или `{count}` внутри него остаются буквальными. В `Notice` передаётся строка, Obsidian выводит её как текст, а не как разметку.

### Форма

`FollowUpsEditor.svelte` работает с черновиками `{ id, text, createdTaskId, marked }`. Черновики собираются из **копии** `task.followUps`, потому что форма получает живой объект задачи из store. Кнопка «→ в бэклог» только помечает черновик. На «Сохранить» `finalizeFollowUpDrafts` обрезает тексты и отбрасывает пустые пункты, в том числе помеченный, но стёртый. Затем применяет лимиты и возвращает список и id помеченных незаведённых пунктов. Эти id уходят вторым аргументом `onSave` (см. «Модальные окна»).

Enter в поле пункта вставляет новый пункт сразу после текущего и не доходит до формы. При вводе через IME (`isComposing`) Enter пункт не вставляет.

У задачи в группе «Завершённые» блок только для чтения: тексты и метки «✓ заведено», без полей и кнопок. При пустом списке блока нет. «Сохранить» оставляет список как был. Причина — незаведённый пункт у закрытой задачи никогда бы не завёлся и пропал бы при автоочистке.

## Автоочистка завершённых задач

При загрузке плагина проверяются задачи в группе «Завершённые»:

```typescript
function cleanupCompletedTasks(board: Board, tasks: Record<string, Task>): void {
  const retentionDays = board.groups.completed.completedRetentionDays ?? 30;
  const cutoffDate = new Date();
  cutoffDate.setDate(cutoffDate.getDate() - retentionDays);

  board.groups.completed.taskIds = board.groups.completed.taskIds.filter(taskId => {
    const task = tasks[taskId];
    if (!task) return false;
    if (!task.completedAt) return true; // нет даты завершения — не удаляем
    const completed = new Date(task.completedAt);
    if (completed < cutoffDate) {
      delete tasks[taskId];
      return false;
    }
    return true;
  });
}
```

Очистка происходит при каждой загрузке плагина. Отдельного уведомления нет — задачи удаляются тихо, так как пользователь сам настроил срок хранения.

## CSS — организация стилей

- **Глобальные стили в `styles.css`** — все стили плагина находятся в одном файле `src/styles.css`. Svelte-компоненты не содержат блоков `<style>`. Сборка использует `compilerOptions: { css: 'none' }`, файл копируется в корень при production-билде
- **Префикс `tm-`** — все CSS-классы плагина имеют префикс `tm-` (например, `tm-task-card`, `tm-empty-state`, `tm-board-layout`). Это предотвращает коллизии с встроенными стилями Obsidian (например, Obsidian использует `.empty-state` с `position: absolute`)
- **BEM-нотация** — классы следуют BEM: `tm-block__element--modifier` (например, `tm-task-card__deadline--overdue`, `tm-collapsible-group__count--over`)
- **Obsidian CSS-переменные** (`--background-primary`, `--text-normal`, `--interactive-accent`) — корректное отображение в любой теме (тёмная, светлая, кастомная)
- **Относительные единицы** (`rem`, `%`, `fr`) — подготовка к мобильной адаптации
- **CSS Grid в теле групп** — `.tm-task-group__body` и `.tm-collapsible-group__body` используют `display: grid` с CSS custom property `--tm-card-columns`. В режиме `single` — 1 колонка (поведение идентично прежнему flex-лейауту), в режиме `multi` — 4 колонки для full-width групп, 2 для half-width. На экранах `<600px` принудительно 1 колонка через media query

## Настройки доски (BoardSettingsPopup)

Popup «...» рядом с названием доски содержит следующие секции:

- **Переименование** — изменение названия и подзаголовка доски
- **Group Visibility** — управление названиями, порядком, видимостью и шириной групп, а также видимостью секции Notes. Строка каждой группы содержит четыре колонки: стрелки перемещения `▲ ▼`, поле названия со счётчиком задач `(N)` (счётчик показывается, если задач больше нуля), чекбокс видимости, чекбокс полной ширины
  - После списка групп — горизонтальный разделитель (`.tm-popup__divider`)
  - Строка секции Notes с чекбоксом видимости (без счётчика — Notes является текстовым полем, а не группой задач)
- **Удаление доски** — с диалогом подтверждения

**Поведение секции Group Visibility:**

- Снятие чекбокса скрывает группу с доски (добавляет `GroupId` в `board.hiddenGroups`)
- Постановка чекбокса возвращает группу на доску (убирает `GroupId` из `board.hiddenGroups`)
- Нельзя скрыть последнюю видимую группу — чекбокс последней оставшейся видимой группы заблокирован (`disabled`) с tooltip-подсказкой
- Чекбокс Notes управляет `board.notesHidden`; нет ограничения «последняя видимая» — Notes можно скрыть независимо от групп
- Кнопка «Cancel» и клик по overlay сбрасывают несохранённые изменения — видимость групп и Notes, ширину, **названия и порядок**: попап целиком работает на локальном черновике и записывает его в store одним вызовом `updateBoard()` по «Save»

**Названия групп в попапе:**

- Поле названия содержит **сохранённое** значение как есть, а не отображаемое: у непереименованной группы поле пустое, а дефолтное локализованное название показано подсказкой ввода (`placeholder`). Сохранение без правок не записало бы шести группам текущие локализованные названия явно
- Ограничение длины — `maxlength=40` на поле ввода; это охрана набора текста, настоящая нормализация выполняется в `updateBoard()` на границе store (см. «Санация полей на каждой загрузке»)
- Очистка поля возвращает дефолтное название — отдельной кнопки сброса нет

**Порядок строк и стрелки:**

- Строки идут в порядке доски (`board.groupOrder`), а не в фиксированном порядке `GROUP_IDS`, — за вычетом идентификаторов, у которых нет объекта группы (см. «Санация полей на каждой загрузке»). Скрытые группы занимают свои позиции наравне с видимыми и не сдвигаются в конец списка
- Строка скрытой группы приглушена (`.tm-popup__group-row--hidden`, `opacity: 0.5`) — приглушение появляется сразу при переключении чекбокса, до сохранения
- Стрелка видимой группы меняет её местами с **ближайшей видимой** соседкой, перешагивая скрытые: обмен со скрытым соседом не дал бы видимого изменения на доске и читался бы как сломанная кнопка. Стрелка скрытой группы двигает её буквально — на соседнюю позицию в списке, независимо от видимости соседа, иначе нельзя выбрать место, где группа появится после возврата видимости
- Стрелка неактивна, когда движение невозможно: у видимой группы — когда в её направлении не осталось видимых групп, у скрытой — когда она уже крайняя в списке. Признак активности и сам перенос построены на общем помощнике внутри `src/ui/groupOrderUtils.ts`, поэтому «стрелка активна» и «перенос состоялся» не могут разойтись. Попап вызывает `canMoveGroup()` для состояния кнопки и `moveGroupWithinPresent()` для перестановки — обе на одном и том же отфильтрованном списке строк
- Стрелки читают **несохранённое** локальное состояние видимости: если снять чекбокс и сразу нажать стрелку, поведение будет соответствовать новому состоянию, а не тому, что записано в файле
- Логика перемещения вынесена в отдельный `.ts`-модуль, а не оставлена в компоненте: код в `.svelte` не покрывается ни unit-тестами, ни `tsc --noEmit`

**Габариты попапа:** шесть строк по пять контролов не помещаются на невысоком экране, поэтому попап ограничен по высоте (`max-height: 80vh`) и прокручивается сам (`overflow-y: auto`). Класс общий с `GroupSettingsPopup` — там строк мало, и ограничение просто не срабатывает.

**Рендеринг доски:**

`BoardLayout` берёт последовательность из `board.groupOrder`, отбрасывает скрытые (`board.hiddenGroups`) и рендерит только видимые — как именно порядок доходит до экрана, описано в разделе «Порядок групп на доске». Секция Notes рендерится условно:

```svelte
{#if !board.notesHidden}
  <div class="tm-board-layout__notes">
    <NotesSection
      boardId={board.id}
      notes={board.notes}
      collapsed={board.notesCollapsed}
    />
  </div>
{/if}
```

Задачи в скрытых группах хранятся в `data.tasks` и в `taskIds` группы — они не удаляются и не перемещаются. Контент Notes сохраняется при скрытии секции и восстанавливается при повторном показе.

## Пользовательские названия групп

Название хранится в `Group.title` и привязано к паре «доска + группа»: одна и та же группа на двух досках может называться по-разному. Набор из шести групп при этом не меняется — переименование не создаёт и не удаляет группы, `GroupId` остаётся служебным идентификатором.

**Пустая строка — не «нет значения», а рабочее состояние.** `title: ''` означает «показывать дефолтное локализованное название», и это же является механизмом сброса: пользователь очищает поле в настройках доски, и группа возвращается к переводу из `i18n`. Отдельного флага «переименована» и отдельной кнопки сброса нет.

Отображаемое название вычисляет одна общая функция:

```typescript
export function resolveGroupTitle(storedTitle: string, defaultLabel: string): string {
  return storedTitle.trim() !== '' ? storedTitle : defaultLabel;
}
```

Функция принимает две строки, а не объект группы: модуль остаётся чистым и не зависит ни от модели данных, ни от i18n-стора — дефолтную подпись добывает вызывающая сторона (`$groupLabels[groupId]`).

**Где показывается название:**

| Место | Компонент |
|-------|-----------|
| Заголовок группы на доске | `GroupHeader.svelte` |
| Заголовок свёрнутой группы (Бэклог, Завершённые) | `CollapsibleGroup.svelte` |
| Заголовок попапа настроек группы | `GroupSettingsPopup.svelte` |
| Строка в настройках доски | `BoardSettingsPopup.svelte` (сохранённое значение, а не отображаемое) |

Смена языка интерфейса переводит только те группы, у которых название пустое; переименованные остаются как есть — пользовательский текст не переводится.

**Подсказка пустой группы** зависит от того, переименована ли группа: у группы с дефолтным названием показывается прежняя подсказка, привязанная к смыслу группы («Что в очереди?» и т.д.), у переименованной — нейтральная (`emptyState.renamed`). Проверка пустоты в `EmptyState.svelte` совпадает с проверкой в `resolveGroupTitle()`, иначе название и подсказка могли бы разойтись.

**Длина.** Предел — 40 символов, и он держится в двух местах: `maxlength` на поле ввода в попапе и `sanitizeGroupTitle()` при записи в store и при загрузке. Длинное название не ломает вёрстку: в заголовке группы оно усекается многоточием (`overflow: hidden` + `text-overflow: ellipsis` + `white-space: nowrap` при `min-width: 0`), в поле попапа — прокручивается внутри поля, не перенося строку и не растягивая сетку.

Название — пользовательский ввод и выводится только через `{}`-интерполяцию (см. «Безопасность»).

## Порядок групп на доске

Порядок хранится в `Board.groupOrder` и задаётся стрелками в настройках доски. На экран он попадает **CSS-свойством `order` на обёртках групп**, а не перестановкой DOM-узлов.

`BoardLayout` строит из `board.groupOrder` массив видимых групп и выводит из него сразу три вещи — какие обёртки рисуются, какой класс ширины получает каждая и какое значение `order` ей достаётся:

```svelte
<script>
  $: orderedGroups = board.groupOrder
    .filter(id => !hidden.has(id) && Object.prototype.hasOwnProperty.call(board.groups, id))
    .map(id => ({ id, fullWidth: board.groups[id].fullWidth }));

  $: groupClasses = computeGroupClasses(orderedGroups);
  $: groupStyles = Object.fromEntries(orderedGroups.map((g, i) => [g.id, `order: ${i + 1}`]));
</script>

{#if renderedGroups.has('focus')}
  <div class={groupClasses['focus']} style={groupStyles['focus']} data-group-container="focus">
    <TaskGroup groupId="focus" ... />
  </div>
{/if}
```

**Почему шесть почти одинаковых `{#if}`-блоков, а не `{#each}`.** Это осознанное решение, а не недоделка. Свёртка в цикл заставила бы Svelte пересоздавать обёртки при изменении порядка, а вместе с ними — уничтожать привязанные к их содержимому инстансы SortableJS. Пользователь получил бы доску, на которой перетаскивание не работает до перезапуска Obsidian, а drag-and-drop проект называет критической функциональностью. При отрисовке через `order` DOM-последовательность шести блоков не меняется никогда: меняется только значение CSS-свойства, инстансы SortableJS остаются живыми, и перетаскивание работает сразу после сохранения нового порядка.

**Конкретика, которую иначе придётся выяснять заново:**

- Нумерация начинается с `1`, а не с `0`: элементы без явного `order` получают `0`. Секция заметок должна оставаться под всеми группами, поэтому у неё задан собственный `order: 100` в `.tm-board-layout__notes` — без него блок заметок всплыл бы над группами. Годится любое число больше шести
- Пары половинной ширины продолжают паковаться в один ряд, даже когда разнесены в разметке: сетка расставляет элементы по `order`, а не по исходной последовательности. `grid-column: 1 / -1` для full-width и `span 1` для half-width работают как прежде
- `computeGroupClasses()` (`src/ui/boardLayoutUtils.ts`) получает уже отсортированный массив и к порядку безразлична — она видит только последовательность и признак `fullWidth`, поэтому «кто с кем в паре» считается по тому же массиву, что и «кто где стоит»
- Условие `{#if}` каждой обёртки проверяет принадлежность множеству отрисовываемых групп, а не истинность значения `order`: при переходе на числовой `order` позиция `0` стала бы falsy и первая группа молча исчезла бы с доски

### Служебные атрибуты для тестов

Три разных атрибута, и они разведены намеренно:

| Атрибут | Где живёт | Что им локализуют |
|---------|-----------|-------------------|
| `data-group-id` | тело группы (`.tm-task-group__body`, `.tm-collapsible-group__body`) | содержимое группы: карточки, empty state, CSS-переменные тела |
| `data-group-container` | обёртка группы на доске (`BoardLayout`) | сама группа как блок доски: `order`, геометрия, заголовок — в том числе у свёрнутой группы |
| `data-settings-group` | строка группы в попапе настроек доски | строка в списке: поле названия, стрелки, чекбоксы |

Почему не один общий атрибут:

- Тело группы отсутствует в DOM, пока группа свёрнута, — по `data-group-id` свёрнутую группу не найти. Поэтому обёртке нужен свой атрибут, присутствующий в обоих состояниях
- Переиспользование `data-group-id` на обёртке дало бы два совпадения на группу. Playwright в strict mode на таком локаторе падает, а `document.querySelector` молча вернул бы обёртку и прочитал бы пустое CSS-свойство — реальная проверка превратилась бы в ложно-зелёную
- Попапу нужен третий атрибут, потому что оверлей не размонтирует доску: попап и доска находятся в DOM одновременно, и локатор строки настроек обязан не совпадать с группой на доске

Атрибуты стабильны относительно названия группы и её состояния — тесты не завязываются на текст заголовка, который теперь редактируется пользователем.

### Известное ограничение: порядок обхода

Порядок обхода с клавиатуры (`Tab`) и порядок чтения экранными читалками следуют разметке, то есть исходной последовательности групп, и расходятся с визуальным порядком, настроенным пользователем. Это принятая цена отрисовки через `order`: альтернатива — перестановка DOM-узлов — ломает drag-and-drop, что для этого плагина хуже. Ограничение относится только к порядку следования групп; внутри группы обход не нарушен.

## Компактный режим карточек

### Визуальная структура

**Обычный режим (default):**
- 3 строки: верхняя (иконки + маркер пост-задач `↪ N` + дедлайн), описание, исполнитель
- Маркер стоит вплотную слева от дедлайна, а без дедлайна — на его месте, справа. Когда маркер есть, дедлайну разрешено сжиматься с многоточием (полная дата — в `title`), иначе в узкой колонке дата заезжала бы под кнопки ☑ и ✕
- Вертикальный layout
- Дедлайн в полном формате: `2026-03-24`

**Компактный режим (compact):**
- 1 строка: иконки → исполнитель → описание → маркер пост-задач `↪N` → дедлайн → кнопка удаления
- Горизонтальный flexbox layout
- Дедлайн в сокращённом формате через `formatDeadlineShort()`

### CSS-реализация

```css
.tm-task-card--compact {
  display: flex;
  flex-direction: row;
  align-items: center;
  gap: 0.5rem;
  padding: 0.35rem 0.5rem;
  min-height: 1.75rem;
  width: 100%;
  min-width: 0;
  overflow: hidden;
}
```

**Ширины секций:**

| Секция | Ширина | Обрезка | Tooltip |
|--------|--------|---------|---------|
| Иконки (приоритет + статус) | `2.5rem` (фиксированная) | Нет | Нет |
| Исполнитель | `7rem` (фиксированная) | `text-overflow: ellipsis` | `title={task.who}` |
| Описание | `flex: 1` (гибкая) | `text-overflow: ellipsis` | `title={task.what}` |
| Маркер пост-задач (только при N > 0) | `1.75rem` (фиксированная) | Нет | Тексты незаведённых пунктов, каждый с новой строки |
| Дедлайн | `4.5rem` (фиксированная) | Нет | Нет |
| Кнопка удаления | `1.25rem` (фиксированная) | Нет | Нет |

**Предотвращение растягивания:**

Для корректной работы обрезки на всех уровнях иерархии установлены ограничения:

```css
.tm-task-group {
  min-width: 0;
  overflow: hidden;
}

.tm-collapsible-group {
  min-width: 0;
  overflow: hidden;
}
```

Это предотвращает растягивание групп и доски длинным содержимым карточек.

### Форматирование дедлайна

Функция `formatDeadlineShort()` (в `utils/dateFormat.ts`) сжимает дату в зависимости от контекста:

```typescript
export function formatDeadlineShort(dateStr: string): string {
  if (!dateStr) return '';

  const today = new Date();
  const deadline = new Date(dateStr);

  if (isNaN(deadline.getTime())) return dateStr; // fallback

  const isSameYear = today.getFullYear() === deadline.getFullYear();
  const isSameMonth = today.getMonth() === deadline.getMonth();

  if (isSameYear && isSameMonth) {
    return deadline.getDate().toString(); // "24"
  }

  const day = deadline.getDate().toString().padStart(2, '0');
  const month = (deadline.getMonth() + 1).toString().padStart(2, '0');

  if (isSameYear) {
    return `${month}-${day}`; // "03-24"
  }

  const yearShort = deadline.getFullYear().toString().slice(-2);
  return `${day} '${yearShort}`; // "24 '27"
}
```

**Примеры:**
- Сегодня 16.02.2026, дедлайн 24.02.2026 → `"24"`
- Сегодня 16.02.2026, дедлайн 24.03.2026 → `"03-24"`
- Сегодня 16.02.2026, дедлайн 24.03.2027 → `"24 '27"`

### Переключение режимов

Изменение настройки `cardView` в Settings Tab вызывает `dataStore.set()` → все компоненты TaskCard реагируют на изменение через reactive-выражение:

```typescript
$: isCompact = $dataStore.settings.cardView === 'compact';
```

Перерисовка происходит мгновенно без перезагрузки плагина.

### Миграция данных

При загрузке старых данных без поля `cardView`:

```typescript
if (result.settings.cardView === undefined) {
  result.settings.cardView = DEFAULT_SETTINGS.cardView; // 'default'
}
```

Обратная совместимость гарантирована — пользователи видят обычный режим до первого изменения настройки.

## Мультиколоночный лейаут карточек

### Визуальная структура

**Режим `single` (по умолчанию):** каждая карточка занимает 100% ширины группы — текущее поведение.

**Режим `multi`:**
- **4 карточки в строку** — для full-width групп
- **2 карточки в строку** — для half-width групп
- Одиночная карточка (и любое неполное количество в строке) занимает 25% ширины, не растягивается
- На экранах `<600px` принудительно 1 колонка через media query

Режим применяется ко всем видам карточек (`default` и `compact`) и переключается глобально в настройках плагина.

### CSS-реализация

Тело группы использует CSS Grid с CSS custom property `--tm-card-columns`:

```css
.tm-task-group__body {
  display: grid;
  grid-template-columns: repeat(var(--tm-card-columns, 1), minmax(0, 1fr));
  align-content: start;
  gap: 0.35rem;
  padding: 0.35rem;
}

.tm-task-group__body > .tm-empty-state {
  grid-column: 1 / -1; /* Empty State занимает всю ширину */
}

/* CollapsibleGroup аналогично */
.tm-collapsible-group__body {
  display: grid;
  grid-template-columns: repeat(var(--tm-card-columns, 1), minmax(0, 1fr));
  align-content: start;
  gap: 0.35rem;
}

/* Мобильные: принудительно 1 колонка */
@media (max-width: 600px) {
  .tm-task-group__body,
  .tm-collapsible-group__body {
    grid-template-columns: 1fr;
  }
}

/* Multi-режим: поле «Что» обрезается в одну строку */
.tm-task-group__body--multi .tm-task-card__what,
.tm-collapsible-group__body--multi .tm-task-card__what {
  display: block;
  -webkit-line-clamp: unset;
  white-space: nowrap;
  overflow: hidden;
  text-overflow: ellipsis;
}
```

### Логика вычисления колонок

В `TaskGroup.svelte` и `CollapsibleGroup.svelte`:

```typescript
$: cardLayout = $dataStore.settings.cardLayout;
$: isMulti = cardLayout === 'multi';
$: columns = isMulti ? (group.fullWidth ? 4 : 2) : 1;
```

Значение `columns` передаётся через CSS custom property `style="--tm-card-columns: {columns}"` на контейнер тела группы.

### Переключение режима

Изменение настройки `cardLayout` в Settings Tab мгновенно перестраивает все группы — аналогично `cardView`.

## Безопасность

- **Запрет `{@html}`** — директива `{@html}` не используется нигде в проекте. Все пользовательские данные (поля задач, названия досок) отображаются через стандартную интерполяцию `{variable}`, которая автоматически экранирует HTML
- **Лимиты длины полей** — текстовые поля ограничены через атрибут `maxlength` на элементах формы: `what` и `why` — 10 000 символов, `who` — 200 символов, `title` доски — 200 символов, `subtitle` доски — 500 символов, текст пункта пост-задачи — 200 символов. Пунктов у задачи не больше 20: кнопка «+ Добавить пункт» и Enter перестают работать на лимите. Оба лимита пост-задач повторно применяются при загрузке (см. «Санация полей на каждой загрузке»)

## Ключевые решения

| Решение | Выбор | Обоснование |
|---------|-------|-------------|
| Идентификаторы | UUID (`crypto.randomUUID()`) | Уникальность без счётчика, безопасно при копировании данных |
| Порядок карточек | Массив `taskIds` в группе | Простой splice при drag-and-drop, нет пересчёта позиций |
| Текстовые поля | Простой текст (textarea) | Markdown-рендеринг избыточен для MVP |
| Момент сохранения | После каждого завершённого действия | Надёжность без потери данных, debounce не нужен |
| Миграции | Поле `version` + последовательные миграции | Безопасное обновление схемы в будущем |
| Хранение задач | Плоский словарь по UUID | Быстрый доступ, простое перемещение между группами |
| Модальные окна | Obsidian Modal + Svelte-компонент внутри | Стандартное поведение (Escape, overlay) + реактивные формы |
| DnD + Svelte | SortableJS ловит жест → отмена DOM → обновление store → Svelte рисует | Один хозяин DOM, нет конфликтов |
| Stores | 3 store: data, ui, plugin | Чёткое разделение: данные / интерфейс / API |
| Формат дат | YYYY-MM-DD, своя утилита | Лёгкий, без внешних библиотек |
| CSS | Глобальный `styles.css`, tm- префикс, BEM | Нет коллизий с Obsidian, поддержка тем |
| Скролл групп | max-height: 50vh + overflow-y: auto | Стабильный layout, автоскролл при DnD |
| Осиротевшие задачи | Очистка при загрузке | Страховка от мусора в data.json |
| Удаление доски | Каскадное + диалог подтверждения | Защита от случайного удаления |
| Дата завершения | Поле `completedAt`, автоочистка по нему | Корректный срок хранения в «Завершённых» |
| Лимиты полей | `what`/`why`: 10K, `who`: 200, `title`: 200, `subtitle`: 500, пункт пост-задачи: 200 (до 20 на задачу) | Защита от раздутия data.json |
| XSS-защита | Запрет `{@html}`, только `{variable}` | Экранирование пользовательского ввода |
| Toast-стакинг | Макс. 3, старый вытесняется новым | Предотвращение засорения экрана |
| Создание доски | Без модалки, дефолтное название | Минимум шагов, переименование через «...» |
| Компактный режим | Flexbox, fixed widths, text-overflow: ellipsis | Плотное отображение для списков с 10+ задачами |
| Дедлайн compact | Адаптивный формат (день / месяц-день / день 'год) | Экономия места, контекстная точность |
| min-width: 0 | На всех уровнях иерархии (group, card) | Предотвращение растягивания flexbox/grid длинным контентом |
| Видимость групп | `hiddenGroups: GroupId[]` в Board, фильтрация в BoardLayout | Простое хранение, задачи не перемещаются, логика не зависит от видимости |
| Защита от скрытия всех групп | disabled чекбокс + tooltip для последней видимой группы | Гарантия рабочей доски, без модального диалога |
| Отмена в BoardSettingsPopup | Cancel и overlay-клик сбрасывают черновик видимости | Безопасное редактирование без немедленного применения |
| Мультиколоночный лейаут | CSS Grid + `--tm-card-columns`, глобальная настройка `cardLayout` | Больше задач на экране без горизонтального скролла; SortableJS поддерживает grid-контейнеры |
| Колонки по умолчанию | `single` (1 колонка) | Обратная совместимость, поведение идентично предыдущим версиям |
| Число колонок в multi | 4 для full-width, 2 для half-width | Пропорционально ширине группы, фиксировано (не настраивается) |
| Мобильный breakpoint | media query `<600px` → 1 колонка | Корректное отображение на узких экранах без логики в JS |
| Видимость Notes | `notesHidden: boolean` в Board, `{#if}` в BoardLayout | Полное удаление секции из DOM; контент Notes сохраняется независимо от видимости |
| Notes в BoardSettingsPopup | Тогл после списка групп, отделён разделителем | Логически связан с Group Visibility, но визуально отделён — Notes не является группой задач |
| Порядок групп | `groupOrder: GroupId[]` в Board, CSS-свойство `order` на обёртках | DOM-последовательность не меняется, инстансы SortableJS выживают, drag-and-drop работает без перезапуска |
| Разметка доски | Шесть литеральных `{#if}`-блоков вместо `{#each}` | Цикл пересоздавал бы обёртки при перестановке и уничтожал бы привязанный к ним SortableJS |
| Порядок секции Notes | Явный `order: 100` в CSS | Элементы без `order` имеют `0` и всплыли бы над группами |
| Название группы | `title: string` в Group, пустая строка = дефолтное локализованное | Одно поле вместо пары «флаг + значение», очистка поля и есть сброс |
| Санация названий и порядка | На каждой загрузке, вне версионных веток | Правленный руками `data.json` чинится и после того, как миграция уже отработала |
| Тестовые атрибуты | Три разных: `data-group-id`, `data-group-container`, `data-settings-group` | Общий атрибут давал бы два совпадения на группу — падение strict mode и молча-зелёные проверки |
| Порядок обхода | Следует разметке, расходится с визуальным порядком | Принятая цена отрисовки через `order`; перестановка DOM ломала бы drag-and-drop |
| Пост-задачи | Список `followUps` внутри задачи, у пункта `createdTaskId` | Отдельные записи удалила бы очистка осиротевших; `createdTaskId` даёт отмене ☑ откатить ровно свои задачи |
| Уведомление о пост-задачах | Obsidian `Notice` из UI-модулей, store возвращает только id | `obsidian` не загружается в unit-тестах store; новый тип toast'а конфликтовал бы с toast'ом завершения того же `taskId` |
